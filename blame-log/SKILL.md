# Blame Log

用户要的是一份能直接贴给对方的日志证据，不是分析报告，也不是方法链讲解。

触发话术包括：甩锅、甩锅日志、日志总结、把这段甩给对方、给对方看的证据。

## 先核对再写

- 只摘已经从原始日志读到的行，禁止凭记忆改写时间、pid、tag、字段
- 日志行必须原样保留，包括空格、大小写、冒号和标点
- 过长的窗口列表可以在不改变关键字段的前提下用 `...` 截断，截断处必须仍能看出 display、窗口名、目标 Activity
- 说明只解释这几行已经证明的事实，不补未出现的调用链，不写修复建议
- 用户指定的故障时间优先于邻近的另一次同类事件

## 输出格式

最终回复不要使用 Markdown。不要用标题、列表、表格、代码块、加粗、反引号。

结构：

1. 开头一行来源，写清日志文件，以及本段用到的 pid 对应进程
2. 每 2 到 3 行原始日志后空一行，再写一句说明
3. 说明和时间顺序一致，先证明己方动作已发出，再证明对方或系统已接收、已完成或已失败

中文说明规则：

- 句子中间不用句号
- 分隔只用空格或逗号
- 行尾也不要句号
- 日志原文里的句号、英文句点、冒号保持不动

## 代码定位（输出前必须先问）

决定使用本 skill 输出时，先停下来问用户一句：是否要增加代码定位。未得到回答前不输出证据文本。

- 回答否：按上面的格式输出，不写任何代码位置
- 回答是：在每一句中文说明末尾加一对括号，括号内写这句说明所对应逻辑在我们自己代码中的位置
- 位置格式：模块相对路径加类名方法名和行号，例如 modules/radio/src/main/java/.../RadioPlayManager.java startScan:1109
- 位置只指向我们自己的代码，对方进程或系统的行不写位置，括号内写 对方代码 或省略括号
- 位置必须来自本次会话中已读取的当前代码，行号以当前文件为准，禁止凭记忆或猜测填写
- 找不到对应代码时，括号内写 未找到对应代码，不得编造
- 括号内的冒号和英文句点保持原样，括号内同样不加句号
- 一句说明对应多处代码时，括号内用逗号分隔，最多写两处
- 加了代码定位后仍然不使用 Markdown，不使用代码块和反引号

## 源代码讲解模式

用户说 用甩锅skill讲解改动代码、用甩锅格式讲解现在的逻辑、把日志换成源代码讲解 时，输出同样的分组证据文本，但证据行换成源代码行。

与日志模式的差异：

- 开头一行写 来源是 工作区源代码，列出每个文件的相对路径和角色，注明行号为当前实际行号
- 证据行从当前工作区文件原样摘取，保留缩进和标点，每组两到三行，整行保留不截断
- 行号必须先用工具在当前文件里核对，禁止凭记忆写，文件刚被修改过必须重新取行号
- 顺序按调用链排列：入口取参，发起请求，校验或过滤，各分支结果，副作用跳转
- 每组后一句说明，句中行尾都不用句号，说明末尾括号写 模块相对路径加类名方法名和行号，最多两处
- 只讲我们自己代码，对方进程或系统不出现；复用的既有方法和未改动但相关的调用点也要列出，说明为何保持原样
- 本模式不需要再问是否增加代码定位，代码位置本身就是内容
- 仍然不使用 Markdown，不使用代码块和反引号

## 证据取舍

优先保留能划清责任的行：

- 己方发出的请求，例如 `showSoftInput`、点击、跳转、接口调用
- 对方进程收到并处理的行，例如输入法、系统服务、对方应用的 tag
- 结果行，例如 `onShown`、`onHidden`、`onCancelled`、错误码、窗口 displayId
- 能反驳“没调用”或“调错屏幕”的行

丢掉心跳、车身信号、重复的同类窗口刷新。同一结论只留最早一条和结果一条。
