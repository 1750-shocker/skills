# Log Evidence Comment

## 目标

把真实日志证据整理成可直接转交责任方的备注。输出必须按时间和因果关系排列，多次循环使用以下结构：

```text
【证据N：一句话证据标题】

```text
<连续、关键、可复核的原始日志>
```

说明：<这段日志直接证明什么，以及不能证明什么。>
```

最后补充总体结论和责任方排查项。

## 触发语义

出现以下意图时启用，不要求用户逐字匹配：

- 总结证据、整理证据、给出日志证据
- 我要备注、整理一段备注、给 Jira 写备注
- 我要转给其他人、转给供应商、转给 HAL/平台/服务端
- 给我日志备注、给出关键日志
- 日志加解释、日志夹说明、每段日志后面写说明

如果用户只要求分析根因而没有要求形成转交备注，先使用对应日志分析或故障诊断技能；分析完成后，用户提出上述意图再使用本技能。

## 前置要求

1. 只能使用已经从真实日志中读取到的内容，禁止编造、改写时间戳、Tag、PID/TID、状态或数值。
2. 尚未完成日志分析时，先调用适用技能提取证据，例如 `android-archive-log-analysis`、`jira-bug-log-analysis` 或其他专项分析技能。
3. 必要时核对源码，明确日志产生方、透传链路和结束条件。
4. 区分四层结论：
   - 用户可见现象
   - 直接原因
   - 上游原因
   - 最早可证实根因
5. 责任归属必须由日志链支撑；证据不足时写“建议某方协查”，不能写成已确认责任。

## 证据选择规则

### 每段日志应证明一个明确命题

优先按以下顺序组织：

1. 故障入口或用户操作确实发生。
2. 上游组件首先出现的异常值、异常状态或错误。
3. 异常值从上游到下游的完整透传链。
4. 用户可见异常与底层状态同时存在。
5. 正常结束事件缺失，或只有取消、超时、异常收尾。
6. 第二次复现与第一次表现一致，排除偶发现象。

### 日志截取原则

- 每段通常保留 3～12 行；需要证明持续性时可稍长。
- 尽量使用连续时间窗口，保留前因、异常点和结果。
- 删除与命题无关的高频噪声，但不能删除会改变因果含义的行。
- 保留原始日志文本，不修正乱码，不把日志翻译后冒充原文。
- 同类循环日志只保留足以证明“持续发生”的代表行。
- 若要证明“没有正常回调”，不能只写“日志中没有”；应同时给出仍在运行、用户取消、随后 `ABORTED`/错误收尾等正向证据，并在说明中表述搜索窗口和缺失项。

## 说明写法

每段日志之后必须紧跟一段简短说明：

- 第一处异常发生在哪一层。
- 关键字段的语义，例如 `IN_PROGRESS`、`ABORTED`、非法范围。
- 该段直接证明的因果关系。
- 如有必要，说明应用是计算、转换还是原样透传。
- 不超过一个自然段，避免重复粘贴日志内容。

推荐句式：

```text
说明：该段形成完整证据链：异常值先出现在 X，随后通过 Y 原样上报到 Z；此时状态仍为 A，因此 B 不是正常完成结果。
```

禁止句式：

- “应该是”“大概是”“看起来像”后直接下责任结论。
- 仅凭时间接近写“由此导致”，但没有状态或调用链证据。
- 把应用收到异常值写成应用生成异常值。
- 把触摸事件到达写成业务操作成功。

## 固定输出结构

### 开头

先用 1～3 句话说明建议转交对象和核心异常，便于接收方快速判断：

```text
建议转 XX 排查。日志中两次均出现……；异常首先产生于……，随后……，且未观察到……。关键证据如下：
```

责任尚未确认时改为：

```text
建议 XX 协查。当前日志最早可确认异常出现在……，但尚缺少……，关键证据如下：
```

### 主体

至少整理 3 段；证据充分时通常为 4～7 段：

```text
【证据1：故障入口正常】

```text
...
```

说明：……

【证据2：上游首次产生异常】

```text
...
```

说明：……
```

证据标题必须直接表达命题，避免“日志1”“现象2”这类无信息标题。

### 结论

使用编号列出完整因果链：

```text
【结论】

1. 上游组件产生什么异常；
2. 通过什么接口或回调上报；
3. 下游如何处理并形成用户可见现象；
4. 正常结束条件为何未满足；
5. 最终通过什么取消或异常路径收尾。
```

仅把日志与代码共同确认的内容写为确定结论。无法确认的内部实现原因单独写：

```text
待责任方确认：该异常值具体由未初始化、计算错误还是参数编码错误造成，现有日志无法区分。
```

### 排查建议

最后给接收方 2～5 个具体检查点，必须来自证据中的组件、字段、版本或状态：

```text
请 XX 侧重点排查：

- 某函数/状态机中字段的初始化与计算；
- 某参数的合法范围及编码；
- 正常完成事件是否可靠发出；
- 日志中出现的具体版本和配置。
```

## 质量检查

输出前逐项确认：

- 每个结论都能指向至少一段日志。
- 第一处异常的组件与建议转交对象一致，或明确写为“协查”。
- 日志展示了时间、Tag、关键状态和值。
- 包含异常如何到达用户界面的链路证据。
- 包含正常完成缺失或异常收尾的证据。
- 多次复现时分别给出证据，不混成一次事件。
- 说明简短、紧随日志，不在结尾统一解释所有日志。
- 没有把推断写成事实。
- 输出可以直接粘贴到 Jira，不添加与转交无关的过程叙述。

## 与其他技能配合

- 本技能负责“证据备注成稿”，不替代原始日志提取。
- Android 归档先用 `android-archive-log-analysis` 定位窗口。
- Jira 附件问题先用 `jira-bug-log-analysis` 获取并分析材料。
- 用户要求代码执行链表格时，另用 `execution-chain-table`。
- 用户要求解释 Bug 原理时，另用 `explainCode`；不要把面向新手的长篇解释混入转交备注。
